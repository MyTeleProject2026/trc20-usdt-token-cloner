# Render configuration — Tron Transfer Owner Admin

Keep the existing `tron-transfer-resource-api` backend, frontend, and Neon database. Do not create replacement services.

Backend environment: NODE_ENV=production, DATABASE_URL (the existing Neon production connection), FRONTEND_ORIGIN (the exact frontend origin), and the existing TRON Mainnet connectivity settings `TATUM_API_KEY`, `TATUM_TRON_NETWORK=mainnet`, `TATUM_TRON_RPC_URL=https://tron-mainnet.gateway.tatum.io`, and `TRONGRID_API_KEY`. The Resource API uses Tatum as its preferred Mainnet read/proxy provider when configured and falls back to TronGrid; TronGrid remains the transaction-history and signed-transaction broadcast path. The Owner/Sponsor transaction engines also use the configured TronGrid Mainnet node for their transaction-specific preflight and solidified-receipt checks. Tatum and TronGrid provide blockchain connectivity only: neither supplies Energy/Bandwidth, sponsors fees, holds wallet keys, or signs transactions. Do not configure GasFree, WDK, Fincra, Fireblocks, third-party treasury, external Sponsor, or provider-payout credentials. Do not add a resource-rental or external Energy/Bandwidth provider. Never put wallet private keys or recovery phrases in Render variables. Neon production currently has one application database named `Tron Transfer Resource Database ` (including the trailing space). Preserve that exact URL-encoded database path and target the `production` branch; do not substitute `neondb` or silently trim the name. The validation branch has a separate `neondb` database, so verify branch and database identity before any migration.

Set `TRON_OWNER_ADDRESS` to the Owner wallet's public Mainnet address (or use `TRON_OWNER_WALLET_ADDRESS` as its alias). The API has no hard-coded Owner address fallback and stays blocked if this value is missing. Owner and Sponsor are two separate wallets owned by the platform owner. Owner signs Owner actions. Sponsor signs Sponsor actions. Sponsor staking/delegation and any TRX transfer to Owner require explicit Sponsor-wallet approval; neither wallet silently signs for the other.

Deploy only an approved commit to the existing services. Confirm migrations and authenticated enrollment readiness before enabling Sponsor writes. Verify Mainnet resources, delegation, transaction persistence, broadcast reconciliation, and recovery. CI success alone is not production readiness.
